# 任务动态（活动流）建模

- Status: accepted
- Date: 2026-08-26

两份 PRD 反复引用「任务动态」，但仓库里既无表、无接口，也无 ADR 说明它是什么：

- 我的工作 PRD §5.3「所有退回动作必填一句话理由，理由随站内通知带给提交人并进任务动态」
- 我的工作 PRD §6.3「所有动作进入任务动态」
- 我的工作 PRD §8.3「已通过｜拟议值成为当前值，进任务动态」
- 我的工作 PRD §8.7「卡点全部系统派生……触发条件消失即自动解除，历史进任务动态」
- MW-18「退回必填理由……理由出现在提交人卡片与任务动态」

本 ADR 定它的口径与边界。ADR 0001 已经定过与之直接相关的一条：**写触发的卡点出现／解除 = 每次写操作前后卡点集合对比差异，写入任务动态；时间型卡点由进程内单 time.Ticker 每小时扫描活跃项目补记动态**。本 ADR 在该前提下细化数据模型与写入点，不推翻它。

## 决定

| 项 | 决定 |
|---|---|
| 形态 | **独立的只追加事实表** `task_activities`，不做读时汇总 |
| 语义 | 一条动态 = 一件已经发生、不可撤销的事实；只记录，不参与任何状态派生 |
| 写入方式 | 每个业务写操作在同一次请求内追加动态；动态写失败不回滚业务动作，只记日志 |
| 卡点留痕 | 按 ADR 0001：业务写操作前后各派生一次卡点集合，按合成键 diff，新增记「卡点出现」、消失记「卡点解除」 |
| 时间型卡点 | 审批超时与任务超期没有触发写操作，按 ADR 0001 应由每小时 ticker 补记；**本版未实现**，见「影响」 |
| 读取 | 只在任务详情按任务倒序返回；不做项目级动态流、不做筛选、不做分页（单任务动态量级很小） |
| 文案 | 面向用户的一句话在写入时定型并落库，读时不再拼装 |

### 为什么不是读时汇总

读时汇总（从 `pool_reviews`、`field_changes`、`completion_reviews`、`discussions`、`input_requests` 五张表 union 出时间线）看起来省一张表，但：

1. **派生卡点没有持久身份**。迁移 00019 已经把 `blockers` 表删掉，卡点是读时从四类结构化事实算出来的，「昨天出现过、今天消失了」这件事在任何现存表里都没有痕迹。要满足 §8.7 的「历史进任务动态」，必须有地方落这条事实——一旦要落，就已经有了事实表，再让其余动态走另一条路只会出现两套口径。
2. **五表 union 的复杂度高于一张表**。每加一种动作就要改 union、改排序、改文案拼装；事实表只需在写入点多一行。
3. **文案会漂**。读时汇总意味着历史动态的措辞随代码变化而变化；PRD 把动态当作留痕（退回理由要"出现在任务动态"），留痕应当定型。

代价是双写：业务事实与动态各写一次，两者可能不一致（动态写失败）。取「动态写失败不回滚业务动作」——动态是留痕，不是业务前置条件，宁可缺一条动态也不能让审批因为记日志失败而回滚。

### 动态类型

| kind | 触发 | 行动人 |
|---|---|---|
| `pool_submitted` | 提交入池审批 | 提交人 |
| `pool_approved` / `pool_rejected` | 入池审批处理（含免审通过） | 处理人 |
| `field_change_submitted` | 提交关键字段修改 | 提交人 |
| `field_change_approved` / `field_change_rejected` | 变更单处理（含免审生效） | 处理人 |
| `field_change_abandoned` | 提交人放弃本次变更 | 提交人 |
| `completion_submitted` | 提交完成申请 | 提交人 |
| `completion_approved` / `completion_rejected` | 中间审核或 KR 终审处理 | 处理人 |
| `blocker_opened` / `blocker_resolved` | 写操作前后卡点集合 diff | 无（系统派生） |

退回类动态的一句话理由直接进 summary，满足 MW-18。

### 不做的

- 不记录讨论意见（讨论 Tab 自己就是平铺时间流，主 PRD §7.5 明确讨论「不等同于审核意见或操作日志」）；
- 不记录进度更新与状态切换（PRD 没有把它们列进动态，且高频写入会淹没审批留痕）；
- 不做项目级动态流与操作审计页面（原型设置页的「操作审计」在本版无数据模型，见 #41）；
- 动态不可编辑、不可删除，也不参与任何规则派生。

## 影响

- 新增表 `task_activities` 与迁移 00021；`TaskDetail` 新增 `activities` 数组，任务详情「概况」Tab 末尾展示。
- 卡点 diff 要求每个业务写操作前后各跑一次项目级卡点派生。当前实现是逐次全量派生，单项目任务量级下可接受；若将来成为热点，按 ADR 0001 的进程内按项目缓存优化，不改动态口径。
- **时间型卡点（审批超时 N×24h、任务超期）目前不会产生动态**：它们不由写操作触发，ADR 0001 规划的每小时 ticker 尚未实现。界面上这两类卡点始终读时派生、显示正确，缺的只是「何时出现」的留痕。补 ticker 时按 ADR 0001 的口径，事件时间戳取计算出的真实发生时刻，而不是 ticker 扫描时刻。
- 双写不一致的可观测性依赖日志；单机自用下不引入对账机制。
